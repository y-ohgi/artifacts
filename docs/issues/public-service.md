# [検討] peta を誰でも使える公開サービスにするために決めること

> 起票済み: [y-ohgi/artifacts#23](https://github.com/y-ohgi/artifacts/issues/23)(`Draft` ラベル)。このファイルとIssueの内容は同一に保つ。

## このIssueの位置づけ

**決定ではなく棚卸し**であり、着手の合図でもない。いま1人用として動いているものを「誰でもサインアップして使えるサービス」にするなら何を決める必要があるかを、現状の実装から逆算して並べる。個別の実装はこのIssueから子Issueへ分割する。

先に結論を書くと、**公開サービス化の可否より先に決めなければならないのは P0 の2件だけ**である。この2件はURLの形に影響し、後から変えると既存のURLが壊れる。残りは公開を決めてから順に片付けられる。

## 名前について

サービス名は **peta(ぺた)** とする。「単体HTMLをぺたっと貼って、URLを渡すための置き場」。検討の記録と理由は `docs/naming.md` にある。

公開サービスにするなら名前まわりで確認・決定が必要なもの:

- [ ] **表記ルールを固定する** — 常に小文字 `peta`。全大文字 `PETA` は使わない(動物愛護団体との混同を避ける)。ロゴも小文字
- [ ] **タグラインを確定する** — 日本語「ぺたっと貼って、URLを渡す。」/ 英語 "Paste an HTML. Get a link."。擬音の由来は説明しない方針(説明が必要な名前は説明せず、動作だけを伝える)
- [ ] **ドメインを確保する** — `peta.*` の空きを確認する。取れない場合の代替(`peta.page` / `petapeta.*` / 既存ドメインのサブドメイン)を決める
- [ ] **識別子の空きを確認する** — GitHub org / リポジトリ名、npm(将来CLIを出すなら)、Slack app名
- [ ] **商標を調べる** — SI接頭辞由来の一般語で識別力が弱く、文字商標単独での登録は難しい前提で考える。ロゴ・図形との組み合わせや修飾語の追加を検討する。**日本国内で誰かが先に「ペタ」系を登録していないかの確認は、ドメイン取得より先に行う**
- [ ] **`peta` を名乗る範囲を決める** — 「貼る」の枠を超える機能(実行環境の提供、SSR、APIホスティング)へ進むなら別サービスとして名前を分ける。この線引きを最初に文書化しておくと、後の機能追加の議論が短くなる

## 現状(2026-07-27 時点)

議論の出発点として、いま何ができていて何が無いかを明示する。詳細は `specs/001-html-artifact-hosting/tasks.md` と `specs/001-html-artifact-hosting/validation-report.md` を正とする。

できていること:

- 単体HTMLのアップロード、一覧、名前の衝突回避、公開/非公開のトグル、`/<uid>/<name>.html` での配信
- 既定は非公開。非公開と不存在の404が本文・ヘッダまで完全に同一
- アーティファクト応答は `Cache-Control: no-store` と `Content-Security-Policy: sandbox ...` 固定
- uidは `a-z0-9` の10文字をCSPRNGで生成(空間は 36^10 ≈ 3.7×10^15)

無いもの・前提に置いていること:

- **認証は Cloudflare Access 前提**。組織の人間を通す仕組みであり、セルフサインアップの経路が無い
- **uidの発行は手作業**(`wrangler d1 execute` で `users` にINSERT)
- **削除・差し替え機能が無い**(spec の Assumptions で初回リリース対象外としている)
- **保持期間は無期限**。容量・件数のクォータも無い
- dev環境は workers.dev の One-click Access でホスト全体が保護されているため、**公開アーティファクトはまだ成立していない**(カスタムドメインへ移してパス単位の保護に切り替えるまで)

### 事実の訂正: 生成物に noindex は付いていない

spec の Assumptions は「公開した生成物を検索エンジンにインデックスさせない方針とする」と書いているが、**この前提は実装されていない**。

- `src/headers.ts` の `ARTIFACT_RESPONSE_HEADERS` に `X-Robots-Tag` は無い
- `<meta name="robots" content="noindex, nofollow">` は `src/views/layout.tsx`(**管理画面のレイアウト**)にしか無く、生成物には及ばない
- 生成物はR2のバイト列を無改変で返すため(FR-012)、そもそもmetaを注入する余地が無い。生成物のインデックスを止める手段は `X-Robots-Tag` ヘッダだけであり、それが無い

したがって「**永続公開されるものは noindex にしない**」という方針転換は、機能の追加ではなく**未実装だった前提を捨てて明文化し直す**作業になる。実装として足りないのは逆側、すなわち**非公開と404側に `X-Robots-Tag: noindex` を付ける**ことである。

## P0 — 公開前に決めないと後から変えられない

### 1. 生成物HTMLを管理画面と同じホストで配り続けるか

いまは `peta.<domain>/_app/*`(管理画面)と `peta.<domain>/<uid>/<name>.html`(生成物)が同一ホストにある。1人用なら問題ないが、誰でもアップロードできるようになると次のリスクが立つ。

- **ドメイン評判の巻き込み**: 誰か1人がフィッシングページを貼って公開すると、ブラウザのセーフブラウジングや企業プロキシ、メールゲートウェイのブロック対象が**ホスト単位**になり得る。そうなると無関係な全ユーザーの生成物と、管理画面までまとめて開けなくなる
- `Content-Security-Policy: sandbox` は生成物を不透明なオリジンへ置くので、生成物のJSから管理画面のCookieやAPIへ触れることは防げている。**しかしドメイン評判の巻き込みは防げない**。別の問題として扱う必要がある
- **インデックスを許すとこのリスクは増幅する**。悪性ページに検索エンジン経由の流入が付くため、「リンクを踏んだ人だけが被害に遭う」状態から「検索から誰でも到達できる」状態になる

選択肢:

1. 現状維持(同一ホスト)
2. ユーザーごとサブドメイン `<uid>.peta.<domain>/<name>.html`
3. 生成物を完全に別ドメインへ分離(GitHubの `*.githubusercontent.com`、Googleの `*.googleusercontent.com` と同じ発想)

- [ ] どれを採るか決める。**2と3はURLの形が変わる**ため、SC-010(既存のURLが1件も変わらない)を守るなら公開ユーザーを受け入れる前に決着させる必要がある
- [ ] 分離する場合、ワイルドカード証明書・DNS・Access application の構成、および `src/index.tsx` のルーティングへの影響を洗い出す

### 2. uidの体系を確定する

現状は運用者が手で発行する10文字のランダム値。自動発行にすると次が必要になる。

- [ ] **予約語**: `_app` / `_auth` / `www` / `api` / `admin` / `abuse` / `cdn-cgi` などを弾く(`_` 始まりは構造的に衝突しないが、サブドメイン方式へ移るなら話が変わる)
- [ ] **ユーザーが好きなuid(ハンドル)を選べるようにするか** — 選べると覚えやすいURLになるが、FR-036(既に発行済みのuidから他を推測できない)と正面から衝突する。非公開アーティファクトのURLの一部であることを踏まえると、**選ばせない**のが素直。選ばせるなら「非公開のURLは推測されうる」という前提へ設計を変える判断が必要
- [ ] 不適切語のフィルタ(自動生成でも 36^10 の空間なら偶然の生成はほぼ無視できるが、選択制にするなら必須)

## P1 — 公開前に必須(URLには影響しない)

### 3. 認証のセルフサービス化

Cloudflare Access はサインアップの仕組みではない。「誰でも使える」にするなら、認証をアプリ側へ持つ必要がある。

- [ ] 方式を決める(OIDC: Google / GitHub、もしくはメールリンク)
- [ ] `/_app/*` の保護境界をAccessから自前セッションへ移す。**ここはいま最も注意深く設計されている部分**(`src/auth.ts` のJWT検証、`src/index.tsx` の保護境界、`/_auth/view` による所有者閲覧の経路)であり、作り直しになる。移行時に「未認証で管理画面の内容が返る」事故が起きないよう、既存のE2E(所有者・2人目・未認証の3視点)を先に拡張してから着手する
- [ ] サインアップ時に自動でuidを発行する経路(P0-2の結論に依存)
- [ ] ログアウトの実装(現状は `/cdn-cgi/access/logout` へ委譲している)

### 4. 削除・差し替えとアカウント削除

- [ ] アーティファクトの削除(R2の実体とD1の行の両方)
- [ ] 差し替え(「貼り替え」)。名前とURLを保ったまま内容を更新できるか
- [ ] アカウント削除時の全データ削除。**誤ってアップロードした情報を消せないサービスを他人に使わせるべきではない**ため、公開の前提条件として扱う
- [ ] インデックスされた後の削除は自サイトから消えるだけである(後述の「取り消せない」を参照)

### 5. SEO / LLMO — 公開したものはインデックスさせる

方針: **`public` になった生成物はすべてインデックス可能とする**。公開状態を3値(一時共有 / 永続公開)へ増やさず、「公開とは、検索とLLMから見つかる状態である」と定義を一本化する。理由は状態が増えるほどUIと権限判定が複雑になり、非公開のものが漏れる事故の面が広がるため。

やること:

- [ ] **`X-Robots-Tag` の出し分け** — `public` には付けない(またはindexを明示)。**非公開と404には `noindex` を付ける**。現在はどちらにも付いていない
- [ ] **`sitemap.xml`** — `public` のものだけを列挙する
- [ ] **`robots.txt`** — 管理画面(`/_app/*`・`/_auth/*`)を明示的に除外する
- [ ] **`llms.txt`** — LLMからの参照を意図するなら用意する。生成物の一覧と要約を機械可読で置く
- [ ] **`Link: rel="canonical"` ヘッダ** — 本文を書き換えずにcanonicalを示せる唯一の手段

構造上できないこと(限界として明記する):

- title・description・OG画像・構造化データは生成物の中身に依存する。**peta は内容を書き換えない(FR-012)ため、SEO/LLMOの品質はアップロード者の責任**になる。「貼るだけ」という名前の含意(`docs/naming.md`)と一貫した制約であり、ここを崩すなら FR-012 を捨てる判断が先に必要
- 代わりに peta が提供できるのは、`sitemap.xml` と `llms.txt` によるクロールの補助、および正しいヘッダだけである

specの変更が必要になる箇所:

- [ ] **Assumptions の noindex 方針を破棄する**(上記「事実の訂正」)
- [ ] **FR-032 を縮小する** — 現行は「公開状態の生成物のページから、同じ利用者の一覧や他の生成物の存在へ到達できる導線を提供してはならない」。`sitemap.xml` に公開物を列挙することはこれに触れる。インデックスさせる以上、FR-032は「**非公開の生成物の存在を漏らさない**」へ縮小する必要がある。FR-024(非公開の存在を判別させない)と、非公開/404の応答同一性は維持する
- [ ] **FR-028 / SC-006 とキャッシュ方針** — 生成物は `Cache-Control: no-store` 固定でCDNキャッシュを捨てている(非公開へ戻した瞬間に見えなくするため)。インデックスを歓迎してトラフィックを受けるなら、`public` にだけ短いTTLを許すかを決める必要がある。SC-006(30秒以内に未認証アクセスを拒否)と整合する範囲のTTLなら両立しうる

**取り消せないことを設計に織り込む**:

- [ ] 一度インデックスされると、検索エンジンのキャッシュやLLMの学習データからは戻せない。`public` → `private` は**自サイトの応答を止められるだけ**で、外部に出た複製は止められない
- [ ] 公開操作のUIに「これは実質取り消せない」と明示し、公開前のプレビューを必須にする。この非対称性が、公開状態を増やさない選択の代償である

### 6. 悪用対策(インデックス許可により前倒しになる)

公開機能はそのまま「任意のHTMLを配信できる基盤」になる。検索に乗るなら、悪用の期待値が上がる分だけ対策の優先度も上がる。

- [ ] 報告窓口(`/abuse` とメールアドレス)とテイクダウンの手順・目標時間
- [ ] アップロードと公開切り替えのレート制限
- [ ] Cloudflare の利用規約・Abuseポリシーとの整合を確認する
- [ ] 公開へ切り替えるときに何らかの検査を入れるか(既知の悪性パターン、外部リソースの参照先など)。**内容を書き換えない方針(FR-012)は維持する**ので、検査は「拒否するか通すか」の判断に限る
- [ ] 既存の防御(`CSP: sandbox` による不透明オリジン化、非公開と不存在の404完全一致)は維持する。インデックス許可はこれらに影響しない

### 7. 規約・運営者情報

- [ ] 利用規約、プライバシーポリシー、運営者の連絡先
- [ ] 保存内容の扱い(運営者が中身を見ることがあるのか、どういう場合か)
- [ ] 免責の範囲(貼られたHTMLの表示品質はアップロード者の責任、という現状の前提を明文化する)
- [ ] 公開したものがインデックスされること、および取り消せないことを規約に明記する

## P2 — 規模が出てから

### 8. マネタイズ — x402 を本線とする

- [ ] **x402 を軸に検討する。** HTTP 402 で本文を返さずに支払いを要求する仕組みなので、**生成物のHTMLを書き換えずに済む**(FR-012を守れる)。Cloudflare 側にも Workers 向けの実装が揃いつつある(`x402-hono` ミドルウェア、Agents docs の "Charge for HTTP content"、Monetization Gateway)。**APIの詳細・価格設定の粒度・手数料は実装前に一次情報で確認する**(今回は公式docsの取得が403で拒否されたため未確認)
- [ ] **課金対象を決める。** (a) 閲覧者に課金(有料アーティファクト) (b) クローラ・AIエージェントに課金 (c) アップロード者に課金(容量や永続公開の対価)
- [ ] **最重要のトレードオフ: (b) と SEO/LLMO は同時に選べない。** クローラに402を返せばインデックスされない。「無料でインデックスさせて認知を取る」か「クローラに払わせて収益を取る」かの二択であり、**ここがマネタイズ検討の入口**になる。なお同じ402ベースの仕組みは Cloudflare の pay per crawl として既に存在するため、(b)を採るなら自作せず済む可能性がある
- [ ] **広告は制約の記録のみ。** 生成物への広告注入はFR-012(内容を書き換えない)と `CSP: sandbox`(不透明オリジンでサードパーティスクリプトが機能しない)に正面衝突する。ラッパーページ方式にするとURLが変わり(SC-010)、sandboxによる隔離設計とも矛盾する。やるならFR-012を捨てる判断が先

### 9. その他

- [ ] **クォータとコスト**: 1人あたりの容量・件数、TTL(現状は無期限)。R2 / D1 / Workers のコスト試算。無料と有料の線引き
- [ ] **監査ログ**: 公開状態の変更履歴、アクセスログの保持期間と目的
- [ ] **UIの多言語化**: 名前が日本語の擬音由来なので、英語UIでは名前を説明せずタグラインで動作を伝える(「名前について」の方針)
- [ ] **単体HTML以外を受けるか**: 画像・PDF・複数ファイル。「貼る」の枠内なので名前は壊れない

## 意図的に今は決めないこと

議論が発散しないよう、以下は「このIssueでは扱わない」と宣言しておく。

- 独自ドメインの割り当て
- チーム・組織単位での共有、閲覧者を個別指定する共有
- パスワード付き共有、有効期限付きURL
- 生成物への埋め込み(iframe)の許可・制限の細分化
- 実行環境の提供(SSR、APIホスティング) — これは peta の枠外(「名前について」の最後の項目)

## このIssueの完了条件

- P0の2件に結論が出ている
- **「インデックスさせて認知を取るか、クローラに課金して収益を取るか」の二択に結論が出ている**
- P1の各項目が子Issueへ分割されている
- 公開サービスにするか否かの判断材料が揃っている(このIssueは「する」と決めるためのものではない)
